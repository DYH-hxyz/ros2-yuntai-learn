```
        │  /cmd_vel 、/odom 、/joint_states 、TF ...                        │
        └──────────────────────────────┬────────────────────────────────────┘
                                       │ 话题
        ┌──────────────────────────────▼────────────────────────────────────┐
        │  ros2_control（ros2_control_node 这一个进程，红框内）             │
        │                                                                │
        │   Controller（diff_drive_controller）                           │
        │      ▲  读状态 get_state(...)      │  写命令 set_command(...)    │
        │      │                            ▼                             │
        │   Hardware Interface（MobileBaseHardwareInterface ← 本包写的）    │
        │      read()/write()/on_init()/on_configure()/on_activate()...    │
        │                                                                │
        └──────────────────────────────┬────────────────────────────────────┘
                                       │ 普通 C++ 函数调用（同一进程/不同库）
        ┌──────────────────────────────▼────────────────────────────────────┐
        │  硬件驱动 Driver（feetech_driver.hpp ← 本包写的，包住厂商 SDK）      │
        │     activateWithVelocityMode / getVelocityRadianPerSec / ...      │
        │     WriteSpec / WheelMode / ReadSpeed / PortHandler...            │
        └──────────────────────────────┬────────────────────────────────────┘
                                       │ 串口字节流（USB 转 TTL）
        ┌──────────────────────────────▼────────────────────────────────────┐

        └───────────────────────────────────────────────────────────────────┘
```

**一句话总结**：硬件接口是「ros2_control 和舵机之间」的桥；驱动是「舵机型号特有逻辑」的封装；
它们各管一层、互不越界。

## 2. 严格区分：硬件 / 硬件驱动 / 硬件接口

| | 硬件接口 (Hardware Interface) | 硬件驱动 (Driver) | 硬件 (Hardware) |
|---|---|---|---|
| **文件** | `mobile_base_hardware_interface.hpp/.cpp` | `feetech_driver.hpp` | 实物舵机（不在代码里） |
| **面向谁** | ros2_control / 控制器 | 舵机型号（Feetech STS） | 物理总线 |
| **认识什么** | 关节名、`velocity`/`position` 接口、rad/s | 舵机 ID、轮子模式、寄存器原始速度值 | 电信号、协议帧 |
| **不认识什么** | 不认识舵机协议 | 不认识 ros2_control / 关节名 | — |
| **调用什么** | `get_command("xxx/velocity")`、`set_state(...)` | `sms_sts::WheelMode/ReadSpeed/WriteSpec` | — |

**为什么必须拆成两层？**

- ros2_control 只认「关节 + 接口 + rad/s」这些**抽象**，它绝不关心你的舵机是飞特还是别家。
- 厂商 SDK 只认「ID + 寄存器 + 原始速度值」这些**具体**，它绝不关心 ros2_control。
- 中间隔着一个「翻译官」= 硬件接口；而「这一型号舵机特有的切换轮子模式、单位换算」= 驱动。

这样换舵机品牌时只改驱动层；换控制器/上仿真时只改接口层——互不牵连。

## 4. 驱动层 feetech_driver.hpp（header-only 包装）

**位置**：`include/my_robot_hardware/feetech_driver.hpp`

**命名说明**：教程里作者的包装类叫 `XL330Driver`，但那是**他那款舵机**的型号；你的舵机是
**飞特 Feetech**，所以本包命名为 `FeetechDriver`（文件 `feetech_driver.hpp`），方法接口与教程保持一致
方便对照。改名只影响“叫法”，不影响任何功能。

**为什么只有 `.hpp` 没有 `.cpp`？**
这个类很小、只是把厂商 SDK 调用和单位换算包一层。函数体直接写在 `class { ... }` 内会自动被视为 `inline`，
即使被多个 `.cpp` include 也不会重复定义。它不单独编译，代码会随 `mobile_base_hardware_interface.cpp`
一起编进插件 `.so`。

**它向外提供的「人话方法」（与教程一一对应）：**

| 方法 | 内部真实调用 | 说明 |
|---|---|---|
| `init()` | `PortHandler::openPort()` + `setBaudRate(1000000)` + 创建 `sms_sts` | 打开串口、设波特率、建高层 API |
| `activateWithVelocityMode(id)` | `sms_sts::WheelMode(id, err)` → 速度归零 | 切到轮子(恒速)模式 |
| `deactivate(id)` | 速度写 0 | 停车 |
| `getVelocityRadianPerSec(id)` | `sms_sts::ReadSpeed(id, raw, err)` | 读回原始速度 → 换算 rad/s |
| `setTargetVelocityRadianPerSec(id, vel)` | `sms_sts::WriteSpec(id, raw, acc, err)` | rad/s → 原始速度 → 下发 |

> 成员用 `std::shared_ptr` 持有 `PortHandler` / `sms_sts`，生命周期自动管理，不用手动 delete。

## 5. 硬件接口层 头文件与源文件（含：这个头文件到底干嘛用的）

### 5.1 你到底卡在哪：旧思路「找到 SDK 直接用」 vs 现在的「分层头文件」

**旧思路（你之前以为的做法）—— 它并没有错，只是适用场景不同：**
```
#include "scservo_sdk/sms_sts.h"        ← “找到 SDK 库” = include 厂商 SDK 的头文件
sms_sts packetHandler(&ph);              ← 直接用
while(1) { packetHandler.WriteSpec(...) } ← 自己写个 while 循环一直调
```
这就是 SDK 里 `sms_sts/wheel.cpp` 示例的写法，**只适用于「不用 ros2_control 的独立程序」**。
在那种写法里确实**没有**“硬件接口头文件”这回事——你 include 的永远是厂商 SDK 的头文件。

**现在为什么“变了”？因为你把舵机接进了 ros2_control：**
- ros2_control **不认识你的 SDK**。它只认一个固定“插座”= `SystemInterface` 基类，
  规定你必须实现 `read/write/on_init/on_configure/on_activate/on_deactivate` 这 6 个函数。
- ros2_control 每周期只会调你的 `read()/write()`，**绝不直接调 `WriteSpec`**。
- 所以你必须**自己写一个类**去实现这个插座，然后把旧 while 循环里“调 SDK 的那段代码”
  **搬进 `read()` 和 `write()` 里**。

**那“硬件接口头文件”到底是干什么的？**
它**不是**取代 SDK，也**不是**新增了什么通信魔法——它只是 C++ 的“先声明、后实现、再使用”：
- `.hpp`（头文件）= **声明**：告诉编译器和其他文件：“有一个类叫
  `MobileBaseHardwareInterface`，它继承 `SystemInterface`、有这 6 个函数、私有成员是
  driver 指针 + 左右电机 ID + 串口名”。
- `.cpp`（源文件）= **实现**：把这 6 个函数“具体怎么做”写出来。
- 没有声明文件，`.cpp` 就不知道“照什么签名填实现”；ros2_control / pluginlib 运行时
  也没法按类名 `mobile_base_hardware::MobileBaseHardwareInterface` 找到并实例化这个类。

**新旧对比一张表：**

| | 旧想法（直接用 SDK） | 现在（硬件接口插件） |
|---|---|---|
| while 循环谁写 | 你自己写 | ros2_control 的 update 循环替你跑 |
| include 什么 | 厂商 SDK 头文件 | 基类 + 我们自己的头文件 |
| 直接调用谁 | `sms_sts::WriteSpec(...)` | 实现 `read()/write()`，里面再调 `FeetechDriver`→`sms_sts` |
| “头文件”指什么 | 厂商 SDK 的头文件 | 给【我们自己写的类】做声明的 `.hpp` |

> **一句话**：不是“头文件取代了直接调 SDK”，而是“直接调 SDK 的代码被装进了类的
> `read()/write()`；头文件是给这个新类做声明用的，让 ros2_control 和 `.cpp` 都知道它长什么样。”

### 5.2 头文件 `mobile_base_hardware_interface.hpp` 具体做了三件事

1. `#include "hardware_interface/system_interface.hpp"` —— 引入基类（拿到 6 个待实现函数的签名、
   以及 `set_state/get_state/get_command`、受保护的 `info_`）。
2. `#include "my_robot_hardware/feetech_driver.hpp"` —— 引入【驱动层】（拿到 `FeetechDriver` 的完整定义，
   因为下面成员要持有一个 `shared_ptr<FeetechDriver>`）。
3. 声明 `class MobileBaseHardwareInterface : public hardware_interface::SystemInterface`：
   - public：6 个 `override` 声明（on_init/on_configure/on_activate/on_deactivate/read/write）；
   - private：`driver_`（驱动指针）、`left_motor_id_`/`right_motor_id_`（电机 ID）、`port_`（串口名）。

### 5.3 源文件 `mobile_base_hardware_interface.cpp` 与“声明/实现分离”

- `.cpp` 里 `#include "my_robot_hardware/mobile_base_hardware_interface.hpp"`，然后逐个写这 6 个函数体。
- 为什么 `.hpp` 只放声明、`.cpp` 放实现？这是 C++ 标准的「声明/实现分离」：
  `.hpp` 告诉别人“这个类长什么样”，`.cpp` 藏住实现细节；编译产物 `.so` 里只有 `.cpp` 的机器码。
  头文件是被 `#include` 的，不单独编译。
- `.hpp` 里（还有 `feetech_driver.hpp` 里）的函数体都写在 `class {...}` 内 = 自动 `inline`，
  所以它们“被 include 进去就能用”，不需要额外编一个 `.o`。

## 6. 六个 override 逐个走读

### ① `on_init` —— 加载插件时最先、只执行一次

```cpp
hardware_interface::CallbackReturn MobileBaseHardwareInterface::on_init(
  const hardware_interface::HardwareComponentInterfaceParams & params)
```

- **Jazzy 注意**：新版签名收的是 `HardwareComponentInterfaceParams`，里面的
  `params.hardware_info` 就是老版 `on_init(const HardwareInfo & info)` 的 `info`（URDF 解析结果）。
  本包用新版签名（和 `mock_components/GenericSystem` 一致），不会触发 deprecation 告警。
- **做了什么**：① 校验 URDF 里正好 2 个关节、且每个关节都有
  `velocity` 命令接口 + `position`/`velocity` 状态接口（diff_drive 要求的）→ 不对就返回 `ERROR`；
  ② 从 `info.hardware_parameters` 读 `port` / `left_motor_id` / `right_motor_id`（读不到用默认值）；
  ③ `driver_ = std::make_shared<FeetechDriver>(port_)` 只构造驱动对象（还没开串口）。
- **为什么不在这里开串口？** 让「真正碰硬件」发生在更靠近运行的 `on_activate`，生命周期更干净。

### ② `on_configure` —— unconfigured → configured

- 本实现留空返回 `SUCCESS`（和教程一致）。真正需要"配置不使能"的动作（如读型号、校准）可放这里。

### ③ `on_activate` —— inactive → active（上电使能）

- **a) 清零全部状态接口**：遍历 `info_.joints` 里每个关节的每个状态接口，`set_state(name, 0.0)`。
  教程里是逐条写 `base_left_wheel_joint/velocity` 等，这里用循环遍历，效果一致且换名字不用改代码。
- **b) 激活驱动**：`driver_->init()` 打开串口（失败返回 `ERROR`）→
  `activateWithVelocityMode(left/right)` 把左右舵机切到轮子模式并归零。

### ④ `on_deactivate` —— active → inactive

- `deactivate(left/right)` 让舵机速度归零停车。

### ⑤ `read(time, period)` —— 控制循环每周期：读状态上报

```cpp
double left_vel  = driver_->getVelocityRadianPerSec(left_motor_id_);
double right_vel = driver_->getVelocityRadianPerSec(right_motor_id_);
set_state("base_left_wheel_joint/velocity", left_vel);
set_state("base_right_wheel_joint/velocity", right_vel);
// 位置用“软件积分”：position += velocity * period
set_state("base_left_wheel_joint/position",
          get_state("base_left_wheel_joint/position") + left_vel * period.seconds());
```

- 速度从舵机真实读回；位置用 `速度 × 周期时长` 积分（里程计/差分控制器需要 position）。
- 若想更准，可把位置也改成从舵机 `ReadPos` 读真实位置（本实现保留积分写法以便对照教程）。

### ⑥ `write(time, period)` —— 控制循环每周期：下发指令

```cpp
double left_cmd  = get_command("base_left_wheel_joint/velocity");
double right_cmd = get_command("base_right_wheel_joint/velocity");
driver_->setTargetVelocityRadianPerSec(left_motor_id_,  left_cmd);
driver_->setTargetVelocityRadianPerSec(right_motor_id_, right_cmd);
```

- 从命令接口取出 diff_drive 算好的轮速(rad/s)，交给驱动层换算下发。

## 7. 生命周期时序：ros2_control 怎么调用你

```
启动 ros2_control_node → pluginlib 加载 libmy_robot_hardware.so
        │
        ▼  ① 仅一次
   on_init(params)          —— 校验 URDF、读参数、创建 driver
        │
        ▼  (configure 过渡)
   on_configure(state)      —— (空)
        │
        ▼  (activate 过渡)
   on_activate(state)       —— 状态清零 + 切轮子模式
        │
        ▼  进入 active，控制循环每 10ms (update_rate=100)：
   read(time, period)  ─┐   读舵机 → set_state（速度+积分位置）
   write(time, period) ─┘   取 get_command → 下发舵机
        │
        ▼  (deactivate 过渡)
   on_deactivate(state)     —— 停车
        │
        ▼  (cleanup/shutdown)
   结束
```

这三个 `on_configure/on_activate/on_deactivate` 是 **rclcpp_lifecycle** 的生命周期回调；
`read/write` 是 **SystemInterface** 的控制周期回调。全部在 `ros2_control_node` **同一个进程**内
被 `controller_manager` 直接函数调用——**不用话题**（话题只用在最外层：`/cmd_vel` 进、`/odom` 出）。

## 8. read/write 与接口机制：set_state/get_command 详解

ros2_control 的「命令接口/状态接口」是一块**进程内共享内存**：

| 方法 | 谁调用 | 环节 | 作用 |
|---|---|---|---|
| `set_state("关节/接口", 值)` | 硬件接口 | `read` 里 | 把硬件状态写进状态接口 |
| `get_state("关节/接口")` | 控制器 / 硬件接口 | `update` / `read` | 读状态值 |
| `set_command("关节/接口", 值)` | 控制器 | `update` | 把目标指令写进命令接口 |
| `get_command("关节/接口")` | 硬件接口 | `write` | 读控制器下发的指令 |

- 接口名格式 = `"关节名/接口名"`，例如 `base_left_wheel_joint/velocity`；
  名字必须和 URDF `<ros2_control>` 里声明的一致。
- 这些名字由「硬件接口在 urdf 里声明」，由「控制器按自己的约定使用」。
  `diff_drive_controller` 要求：每个轮关节有 `velocity` 命令接口 + `position`/`velocity` 状态接口。
  （若换别的控制器，接口名要跟着换一套。）

## 9. 单位换算：rad/s 与舵机原始速度值

STS 舵机速度寄存器 1 个单位 ≈ **0.732 rpm**，而 ros2_control 用 **rad/s**：

```
rad/s = 原始速度值 × 0.732 × (2π / 60)
原始速度值 = rad/s ÷ (0.732 × 2π / 60)
```

`feetech_driver.hpp` 里 `kRawUnitToRadianPerSec = 0.732 * (2*M_PI)/60`：
- 读：`getVelocityRadianPerSec` 把 `ReadSpeed` 的 raw 乘上它 → rad/s；
- 写：`setTargetVelocityRadianPerSec` 把 rad/s 除以它、四舍五入成整数 → `WriteSpec`。

轮子模式下速度可正可负（正=正转、负=反转）；`WriteSpec` 内部用符号位处理负值。

## 10. CMake 全解：SDK 怎么被编进来、插件怎么导出

### 10.1 两个“世界”回顾

- **世界一（同工程内按 target 身份链接）**：`ftservo_sdk/CMakeLists.txt` 用 `add_library(scservo_sdk ...)`
  在**同一 CMake 会话**里建了 `scservo_sdk` target。外层 `add_subdirectory(ftservo_sdk)` 后，
  `target_link_libraries(my_robot_hardware scservo_sdk)` 直接按身份链接，**不需要 find_package**。
- **世界二（外部包用 find_package）**：ROS 的 `hardware_interface/pluginlib/rclcpp` 是系统装好的外部包，
  用 `find_package(... REQUIRED)` 找（它们各自经 `ament_package` 导出过 `Config.cmake`）。

### 10.2 为什么把 SDK 做成子工程，而不是直接链 `.a`？

`src/sts_text` 里的 `libscservo_sdk.a` 是**手工** `cmake .. && make` 编的，colcon 不知道它、不负责重编它；
跨包引用脆、别人 clone 后不一定有。把它 **vendor 进本包并用 `add_subdirectory`** 后：
`colcon build` 会自动编它 → 整个工作区一键构建、可移植、不依赖外部手工产物。

### 10.3 本包 CMakeLists 关键点

```cmake
set(CMAKE_POSITION_INDEPENDENT_CODE ON)   # 静态 SDK 也要 -fPIC，才能进共享插件
add_subdirectory(ftservo_sdk)             # 拉进 SDK，产出 scservo_sdk target
add_library(my_robot_hardware SHARED      # 插件必须是共享库(.so)，pluginlib 靠 dlopen 加载
  src/mobile_base_hardware_interface.cpp)
target_link_libraries(my_robot_hardware
  scservo_sdk                             # SDK（PUBLIC 传递 include 与 serial）
  hardware_interface::hardware_interface  # SystemInterface 基类
  pluginlib::pluginlib
  rclcpp::rclcpp
  rclcpp_lifecycle::rclcpp_lifecycle)
pluginlib_export_plugin_description_file(hardware_interface my_robot_hardware.xml)
ament_export_libraries(my_robot_hardware)
ament_export_include_directories(include)
ament_export_dependencies(hardware_interface pluginlib rclcpp rclcpp_lifecycle)
ament_package()
```

- `target_include_directories(scservo_sdk PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})`（在子工程里）：
  使 `#include "scservo_sdk/sms_sts.h"` 能找到，并随链接自动传递。
- `add_library(... SHARED)`：**必须**。否则编成 `.a`，pluginlib 加载不了。
- `pluginlib_export_plugin_description_file(...)`：把插件 xml 拷到 `share/` 并写进资源索引。

## 11. pluginlib 插件注册与 urdf 对接

### 11.1 `my_robot_hardware.xml` 三要素

```xml
<library path="my_robot_hardware">                 <!-- 对应 libmy_robot_hardware.so -->
  <class name="my_robot_hardware/MobileBaseHardwareInterface"
         type="mobile_base_hardware::MobileBaseHardwareInterface"
         base_class_type="hardware_interface::SystemInterface">
```

| 字段 | 含义 |
|---|---|
| `library` | 库文件名去掉 `lib` 前缀和 `.so` 后缀 |
| `name` | 插件「名字」，urdf 的 `<plugin>` 里写它 |
| `type` | 类真正的 C++ 全名（带命名空间） |
| `base_class_type` | 基类类型（ros2_control 认 `SystemInterface`） |

### 11.2 urdf 里切换（未来启用真实舵机时）

把 `mobile_base.ros2_control.xacro` 的 `<ros2_control>` 里：
```xml
<plugin>mock_components/GenericSystem</plugin>
```
换成：
```xml
<plugin>my_robot_hardware/MobileBaseHardwareInterface</plugin>
<param name="port">/dev/ttyACM0</param>
<param name="left_motor_id">10</param>
<param name="right_motor_id">20</param>
```

## 12. 如何启用与验证（下一步）

> ⚠️ 本包**尚未**把 urdf 切成真实硬件（切了会破坏你现在的 mock 仿真），所以这里只列步骤，未替你执行。

1. **编译**（已完成验证）：`colcon build --packages-select my_robot_hardware`，产出
   `libmy_robot_hardware.so`，插件索引与符号已确认存在。
2. **想先不接舵机测“能不能加载/configure”**：临时写一份「只加载插件」的最小 urdf（把 plugin 换成我们的，
   关节保持 2 个、接口保持 velocity/position/velocity），跑 `ros2 control` 起 controller_manager，
   观察 `on_init`/`on_configure` 日志是否 `SUCCESS`。activate 需要真实串口舵机。
3. **接真舵机**：插 USB 转 TTL → `ls /dev/ttyACM* /dev/ttyUSB*` 确认设备名 → 在 urdf 的 `<param>` 里配好
   `port` 和两个 `left_motor_id/right_motor_id` → 把 urdf `<plugin>` 换成
   `my_robot_hardware/MobileBaseHardwareInterface` → 重新 `colcon build`（含 description/bringup）→
   `ros2 launch my_robot_bringup my_robot.launch.xml` → 发 `cmd_vel` 观察车轮与 `/odom`。
4. **权限**：如果 `Failed to open the port`，`sudo usermod -aG dialout $USER` 后重登。

## 13. 常见问题 / 排查

| 现象 | 原因 / 处理 |
|---|---|
| `Failed to open the port` | 设备名不对或没权限：查 `ls /dev/ttyUSB*`；加入 `dialout` 组重登 |
| `期望 2 个关节...`（on_init 报错） | urdf `<ros2_control>` 关节数不是 2 |
| `...缺少 velocity 命令接口或 position/velocity 状态接口` | urdf 接口声明不全，对照第 5 节补 |
| 控制器激活失败：找不到命令接口 | 接口名/关节名拼写不一致，对照第 8 节 |
| 舵机不回包 / 超时 | ID 对不对、波特率档位是否 1M、供电够不够、共地 |
| 一运动就 RX_CORRUPT | 波特率不一致 / 线材干扰 / 接触不良 |
| 换舵机品牌 | 只改 `feetech_driver.hpp`（驱动层），硬件接口不用动 |
